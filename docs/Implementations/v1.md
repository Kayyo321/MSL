## 1. Release boundary

### 1.1 Supported host

V1 supports exactly:

- Apple-silicon Macs (`arm64`).
- macOS 14 Sonoma or later.
- One logged-in, non-root macOS user running one per-user MSL service.
- Virtualization.framework available and usable by that user.

V1 does not support Intel Macs, macOS versions before 14, running as root,
multiple host users sharing one MSL state directory, or a privileged helper.
MSL must not request Full Disk Access.

### 1.2 Supported guest

V1 supports exactly one distribution image:

- Debian GNU/Linux 12 “bookworm”.
- `arm64` architecture.
- One MSL-published, signed, immutable image identified by SHA-256 digest.
- Debian systemd enabled as PID 1.

The CLI accepts `debian` as the only distribution name and `12` as the only
release. It must reject `ubuntu`, `fedora`, `arch`, `alpine`, every other
distribution, every other release, arbitrary image URLs, local image paths,
and non-arm64 images. The image catalog may later contain additional Debian
12 image revisions, but an installed instance always records the exact image
digest it used.

### 1.3 V1 user outcome

The following flow is the release-critical path:

```text
msl install debian --release 12 --name debian-dev --user dev
msl shell debian-dev
```

It creates a persistent Debian VM, creates the requested non-root Linux user,
starts a login shell, preserves the guest filesystem across reboots, permits
explicitly approved macOS folder sharing, and permits loopback-only guest
service forwarding.

## 2. Explicit v1 scope

### 2.1 Included

V1 must implement all of the following:

1. Debian 12 arm64 image installation and verification.
2. Persistent VM start, stop, shell attachment, list, and inspection.
3. Per-user state and recovery after daemon restart or interrupted operations.
4. Explicit read-only and read-write macOS directory grants through VirtioFS.
5. Guest outbound NAT networking and stable host name `host.msl.internal`.
6. Explicit TCP guest-to-Mac forwarding bound only to Mac loopback.
7. A versioned `msl.toml` project manifest and optional ignored local override.
8. Project workspace mounting at `/workspace`.
9. One bootstrap command and declared systemd transient project services.
10. Service health checks, project status, logs, and project shutdown.
11. Snapshot, restore, export, import, and safe instance removal.
12. Read-only diagnostics (`doctor`) and one-check-at-a-time repair.
13. Authenticated local CLI-to-daemon IPC and VM-local guest-agent IPC.
14. Structured redacted logs and fixed exit codes.

### 2.2 Explicitly excluded from v1

The following are deferred and must not be implemented as implicit or partial
v1 behavior:

- Any guest distribution or release other than Debian 12 arm64.
- Intel hosts, x86 guests, Rosetta, emulation, or nested virtualization.
- A graphical desktop, GUI applications, audio, camera, or display support.
- USB, Thunderbolt, GPU, Bluetooth, serial, block-device, or device passthrough.
- LAN or internet exposure of guest services.
- UDP forwarding, privileged ports, wildcard host binds, or firewall changes.
- Arbitrary host command execution from Linux.
- Host Keychain access, clipboard reads, arbitrary host-file reads, or secrets
  injection into the guest.
- Docker, containerd, Kubernetes, or a container orchestration UI.
- Multi-VM networking, bridged networking, VPN routing, or custom DNS servers.
- Automatic guest package upgrades or automatic Debian release upgrades.
- Automatic disk growth, disk shrinking, live CPU/memory changes, or VM cloning.
- Hot-plugging shares or devices while a VM is running.
- GUI configuration, auto-update UI, telemetry, cloud synchronization, or
  remote management.
- Arbitrary user-provided kernels, initrds, distributions, or image URLs.
- Live migration, snapshots of running VMs, or cross-host snapshot restore.
- Automatic service restart policies beyond systemd's explicitly configured
  transient unit behavior.

## 3. Product shape and process ownership

V1 consists of exactly these artifacts:

| Artifact | Execution context | Required responsibility |
| --- | --- | --- |
| `msl` | Calling macOS user | Parse CLI, parse manifests, display results, call `msld`. |
| `msld` | Same user, launchd agent | Own VM, disk, image, bookmark, listener, and state mutations. |
| `msl-guest-agent` | Root inside Debian VM | Expose only the VM-local shell/service/status protocol. |
| `MSLCore` | Shared Swift library | Types, schema, validation, IPC messages, errors, serialization. |

The implementation language is Swift 5.10 or later. The VM implementation uses
Virtualization.framework, a verified Debian kernel/initramfs, one writable
sparse root disk, one NAT virtio NIC, one virtio console, one virtio control
socket, and one VirtioFS device per active folder grant.

`msld` is launched by a per-user LaunchAgent. It does not listen on TCP or UDP.
The CLI never writes the database, disk, image cache, bookmark store, or
listener state directly.

## 4. State, storage, and recovery

The state root is exactly:

```text
~/Library/Application Support/MSL/
  state.sqlite3
  images/cache/<sha256>/
  instances/<instance-uuid>/
    config.json
    disk.img
    nvram.bin
    runtime/
    logs/
    snapshots/<snapshot-uuid>/
  exports/<export-uuid>.mslpack
  locks/
```

The state root and all instance directories are mode `0700`. Files containing
state, tokens, bookmarks, or configuration are mode `0600`. Instance, snapshot,
export, and grant IDs are lowercase UUIDs and are never supplied as path
components without database lookup.

SQLite is authoritative. It uses WAL mode, foreign keys, and
`synchronous=FULL`. Required tables are `instances`, `images`, `folder_grants`,
`port_grants`, `operations`, `snapshots`, and `project_runs`. Schema migrations
are versioned and transactional.

An instance has exactly one state:

```text
stopped | starting | running | stopping | error | repair_required
```

Only one mutating operation may run for an instance. Every mutation journals its
intent before changing a disk, database row, bookmark, mount, or listener. On
restart, an incomplete operation is resumed only when its recovery record makes
that action idempotent; otherwise the instance becomes `repair_required` and
cannot start until the user runs the named repair or removes the instance.
Interrupted work is never reported as successful.

## 5. Image and installation contract

The signed catalog is compiled into or securely fetched by `msld` and validated
against a compiled trusted public key. The catalog entry must contain:

- distribution `debian`;
- release `12`;
- architecture `arm64`;
- image URL and declared byte size;
- root image SHA-256 digest;
- kernel and initramfs digests;
- guest-agent compatibility range; and
- catalog signature and optional key-rotation record.

The exact install sequence is:

1. Validate host architecture, macOS version, virtualization availability,
   requested distribution/release, instance name, Linux username, disk size,
   and available host storage.
2. Validate the catalog signature and select a non-revoked Debian 12 arm64
   entry.
3. Download to a unique temporary file while enforcing the declared size.
4. Verify SHA-256 and only then rename into the content-addressed cache.
5. Create the instance database row and disk through one recoverable operation.
6. Boot the VM with signed seed data.
7. Require authenticated guest-agent readiness within 60 seconds.
8. Verify the requested user exists and can start a login shell.
9. Stop the VM cleanly and mark the instance `stopped`.

Any failure leaves no usable instance, except a first-boot failure, which leaves
the instance as `repair_required` with its console log retained. A failed or
interrupted download is deleted. The daemon rehashes cached image artifacts
before use if they are older than 30 days or their filesystem metadata changed.

Default instance resources are 2 vCPUs, 2048 MiB memory, and a 30 GiB logical
disk limit. The initial disk allocation requires the requested allocation plus
10 GiB free on the host. The disk limit can only increase through
`msl instance resize`; it never shrinks or grows automatically.

## 6. CLI contract

These are the only v1 command families:

```text
msl install debian --release 12 --name NAME --user USER [options]
msl shell NAME
msl instance list
msl instance inspect NAME
msl instance start NAME
msl instance stop NAME
msl instance resize NAME --disk GIB
msl instance remove NAME [--permanent --yes]
msl share list NAME
msl share add NAME [HOST_PATH] --guest-path /mnt/mac/PATH [--read-only]
msl share remove NAME GRANT_ID
msl port list NAME
msl port add NAME GUEST_PORT [--host-port HOST_PORT]
msl port remove NAME PORT_ID
msl project validate
msl project up
msl project down
msl project status
msl project logs [SERVICE]
msl project shell
msl snapshot create NAME SNAPSHOT_NAME
msl snapshot list NAME
msl snapshot restore NAME SNAPSHOT_NAME
msl snapshot delete NAME SNAPSHOT_NAME
msl export NAME --output PATH [--include-logs]
msl import PATH --name NAME
msl doctor [NAME]
msl doctor repair NAME CHECK_ID
```

`--json` is supported on every command. JSON mode emits exactly one JSON object
to stdout, never prompts, and sends progress to stderr. Human mode prompts only
when stdin and stdout are terminals. `--yes` bypasses a confirmation but never
selects a directory or grants macOS access.

Exit codes are fixed: 0 success; 1 unexpected internal failure; 2 invalid
argument, manifest, or configuration; 3 missing, stale, or denied macOS
permission; 4 unsupported or unavailable host capability; 5 resource,
operation-lock, or port conflict; 6 image, snapshot, export, or integrity
failure; and 7 guest action, boot, health, or service failure.

When no instance is named for `msl shell`, MSL uses the nearest project
manifest's selected instance only if exactly one instance matches it. With no
manifest, exactly one installed instance is required. MSL never uses last-used
state.

## 7. Folder sharing and permissions

Before a grant exists, the guest cannot see macOS files. A share is an explicit
per-instance security-scoped bookmark containing one canonical host directory,
one guest path, and one mode: read-only or read-write.

The guest path must be absolute, normalized, below `/mnt/mac/`, and contain no
`.` or `..` segment. `/workspace` is reserved for project workflow and cannot
be added manually. MSL rejects the filesystem root, the whole home directory,
`Library`, system directories, duplicate grants, and nested grants.

Interactive `share add` opens the native directory picker. A typed host path is
accepted only when the calling process already has macOS permission to read it;
typing the path never creates permission. The user must see host path, guest
path, mode, and instance before confirmation.

Share additions and removals are pending until the next VM start. MSL never
hot-plugs VirtioFS. Removing a share stops project services using that share,
detaches it on the next stop, revokes the bookmark, and never deletes host files
or guest-disk files.

The guest mount table contains only opaque grant IDs, guest paths, and modes. It
never contains host paths or bookmark bytes. MSL reports, but does not disguise,
case sensitivity, ACL, extended-attribute, symlink, and executable-bit
differences between a macOS share and the Debian ext4 disk.

## 8. Networking and forwarding

Each VM has ordinary outbound NAT. Debian can reach the Mac through the stable
hostname `host.msl.internal`; its numeric address is not a supported interface.

V1 forwarding supports TCP only, for guest ports and host ports `1024..65535`.
The host listener binds exactly to `127.0.0.1` and `::1` when IPv6 is available.
It never binds `0.0.0.0`, `::`, a LAN address, or a privileged port. MSL never
changes the firewall.

If `--host-port` is omitted, MSL allocates and persists a free port in
`49152..65535`. If the requested host port is occupied, the command fails with
exit code 5 and does not select another port. Removing a port closes only the
Mac listener; it does not stop the guest process. A guest service listening only
on guest loopback cannot be forwarded.

## 9. Project manifest

The repository file `<project>/msl.toml` must contain exactly this v1 schema:

```toml
schema = 1
distribution = "debian"
release = "12"
workspace = "."

[resources]
cpus = 4
memory_mib = 4096
disk_gib = 40

[bootstrap]
command = "./.msl/bootstrap.sh"
timeout_seconds = 900

[[service]]
name = "web"
command = "npm run dev -- --host 0.0.0.0"
working_directory = "."
port = 3000
host_port = 0
health = "http://127.0.0.1:3000/health"
health_timeout_seconds = 60
```

Required fields are `schema`, `distribution`, `release`, `workspace`, every
resource field, every bootstrap field, and `name`, `command`, `working_directory`,
and `port` for every service. `host_port` defaults to `0` and
`health_timeout_seconds` defaults to `60`. The only accepted distribution and
release values are `debian` and `12`.

Validation rules are exact:

- `schema` is integer `1`.
- Resource CPU count is an integer from 1 through host logical CPU count.
- Memory is 1024 MiB through host-available-minus-1024 MiB in 256 MiB steps.
- Disk is 10 through 1024 GiB and cannot be below current disk usage.
- Workspace resolves to one directory inside the manifest directory.
- Service names match `^[a-z][a-z0-9-]{0,31}$` and are unique.
- Service commands are non-empty UTF-8 strings no longer than 4096 bytes.
- Working directories resolve inside the workspace.
- Guest ports are TCP integers from 1024 through 65535 and are unique.
- Host ports are `0` or integers from 1024 through 65535 and are unique.
- Health URLs are HTTP(S), target `127.0.0.1` or `localhost`, and use that
  service's port. Without `health`, the health check is a TCP connect.
- Unknown keys, duplicate TOML keys, duplicate service names, empty commands,
  and invalid paths are errors.

`msl project validate` performs all syntax, schema, workspace-permission,
resource, image-catalog, and port checks and changes nothing.

### 9.1 Local override

`msl.local.toml` is loaded only when that exact file is ignored by Git. If Git is
not available, it is rejected unless the user explicitly passes
`--allow-local-config` to the project command.

The override may change only `resources.cpus`, `resources.memory_mib`,
`resources.disk_gib`, a named service's `host_port`, and a named service's
`health_timeout_seconds`. It may not add or remove a service, change the Debian
image, workspace, commands, working directories, guest ports, or health URLs.

## 10. Project lifecycle

`project up` performs these steps in order: validate the manifest and allowed
override; resolve the workspace and obtain explicit authorization; install or
select the exact Debian 12 image; create or reconcile one project instance;
apply resources while stopped; mount the workspace at `/workspace`; start and
authenticate the guest; run bootstrap; start declared transient services; check
each service once per second until timeout; create declared loopback-only
forwards; and print authoritative URLs.

Bootstrap runs as the designated Linux user in `/workspace` with only
`MSL_PROJECT=1` added to its environment. It runs once when the effective
manifest, local override, selected image digest, or workspace bookmark hash
changes. Failure or timeout stops services started by that invocation, preserves
the VM and workspace, exits 7, and does not retry automatically.

Services use transient unit names
`msl-project-<project-id>-<service>.service`. An early exit before health,
closed TCP health check, or HTTP response outside 200..399 fails `project up`.
After a service becomes healthy, later failure is reported as `unhealthy` or
`exited`; MSL does not restart it automatically. `project down` stops only the
effective project's services and forwards.

## 11. Snapshots, transfer, and removal

Snapshots require a stopped VM. Creating one captures the consistent root disk,
generated VM configuration, image digest, and metadata. Restoring first creates
an automatic pre-restore snapshot, requires the exact snapshot name, and then
atomically replaces the disk. Host grants, port grants, and active secrets are
never restored. A partial restore is never booted; interrupted restore produces
`repair_required`.

Exports require a stopped VM and contain the root disk, generated configuration,
and signed manifest. They exclude host bookmarks, port forwards, active secrets,
and logs unless `--include-logs` is present. Export refuses to overwrite an
existing file without `--overwrite`.

Import validates archive integrity, assigns a new UUID, never overwrites an
instance name, and restores no host grants or port forwards.

Removal displays the exact name, UUID, disk size, and snapshot count and
requires typing the instance name or using `--permanent --yes`. It stops the VM,
revokes grants and listeners, moves the exact instance directory to macOS Trash
when available, and deletes database rows transactionally. If Trash is
unavailable, removal refuses unless `--permanent --yes` is supplied. The shared
image cache is never removed by instance removal.

## 12. Security, privacy, and logging

The CLI connects only to a Unix socket in a `0700` runtime directory. The socket
is `0600`; `msld` verifies peer UID and a daemon-issued 256-bit session token.
IPC is length-prefixed JSON with a 1 MiB message limit, request IDs, protocol
major-version checks, and rejection of unknown methods, duplicate IDs, malformed
JSON, and oversized messages.

The guest agent is reachable only through a virtio socket. Each boot receives a
new 256-bit handshake secret through read-only VM configuration; the secret is
discarded on stop. The agent exposes only `status`, `exec_shell`,
`service_apply`, `service_stop`, `service_status`, `health_check`, and
`shutdown`.

Logs are newline-delimited JSON containing timestamp, component, severity, event
code, operation ID, instance UUID, and redacted message. Logs must not contain
bookmark bytes, tokens, passwords, command arguments, environment values,
clipboard data, shared-file contents, or full project paths. Console logs are
local-only and bounded to 50 MiB across the current file plus ten rotated files.

## 13. Diagnostics

`msl doctor` is read-only and checks exactly: macOS version, architecture,
Virtualization.framework, host storage, image catalog/cache integrity, database
state, bookmark validity, VirtioFS mounts, loopback listeners, NAT/DNS,
guest-agent readiness, and project-service health.

`msl doctor repair NAME CHECK_ID` accepts exactly one previously failed named
check, explains the proposed action, and changes only resources owned by that
check. It never deletes a disk, snapshot, export, database, or host directory
automatically.

## 14. Implementation order and release gates

Implementation must proceed in this order, with the preceding stage passing its
tests before the next stage is merged:

1. `MSLCore`: identifiers, errors, manifest schema, config merge, and IPC types.
2. `msld` state store: schema, locks, journals, migrations, and recovery.
3. Signed Debian 12 catalog and image cache verification.
4. VM creation, boot, guest-agent handshake, shell attachment, and shutdown.
5. Explicit bookmark grants and VirtioFS mount reconciliation.
6. NAT, host name, loopback-only TCP forwarding, and conflict handling.
7. Project validation, workspace lifecycle, bootstrap, services, and health.
8. Snapshots, restore, export, import, and removal safety.
9. Doctor, repair, structured logging, and security regression tests.

V1 is releasable only when a clean Apple-silicon macOS 14 account can install
the signed Debian 12 image and obtain a shell; every included command and
invalid-input rule has an automated test; a guest service is reachable only
through Mac loopback; a repository works in `/workspace`; interrupted install,
failed bootstrap, stale bookmark, port conflict, and interrupted restore are
recoverable; and no security, privacy, integrity, or destructive-operation test
failure is waived.

## 15. Deferred roadmap

The following require a separate design and verification update before
implementation: additional Debian releases or distributions; Intel or emulated
guests; VM cloning and live resize; LAN opt-in exposure, UDP, custom binds, or
bridged networking; GPU/USB/audio/display; container runtimes; GUI/cloud
management; multiple concurrent project environments; remote development and
multi-user hosts; and automatic Debian package or release upgrades.

None may be added to v1 through undocumented flags, permissive parsing,
wildcard networking, arbitrary image support, or best-effort fallbacks.
